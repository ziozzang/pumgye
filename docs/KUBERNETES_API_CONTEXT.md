# Explicit Kubernetes API policy context (core prerequisite)

The deterministic core supports `authorization_context: "kubernetes_api"` on an explicitly opted-in native service. It uses the existing users/roles/permissions/information-class/resource catalog in the same `CompiledPolicy`. This is a network-free API authorization context: the compiler requires `require_guard: false`, empty `networks`, empty `workload_users`, and every assigned subject in the `k8sapi:` namespace. It does not fabricate an IP address or Sumunjang `EnforcedAllow`.

Omitting the field retains the existing `network_and_guard` context and serialization. The ordinary service, unscoped resource, scoped resource and Workload resource evaluators refuse a Kubernetes API service. Conversely, `evaluate_kubernetes_api_resource` refuses an ordinary service. Existing network/guard conjunctions cannot be bypassed by choosing the new entrypoint.

The new method takes a `KubernetesApiSubject` metadata label, fixed service/resource/action, and no IP, guard or caller assurance. It evaluates existing grants, catalog-owned classification and role/resource minimum assurance with actual assurance fixed at0. A role or resource requiring AAL1+ therefore denies. Parsing a namespaced label proves syntax only; it authenticates no API server or user and is neither a Hopae Human/Service/Workload principal nor a capability. The caller must authenticate the API server and resolve a server-owned identity/resource mapping before invoking the core.

For example, a future trusted API-server mapping may select subject `k8sapi:cluster-a:reader`, service `k8s-config`, resource `k8s:blue:settings` and action `get`. The native policy must independently grant its read permission and information class. A different subject, service, action or missing grant denies. A compiled snapshot is immutable: deleting a grant affects a newly compiled publication; the server must still fence the exact current View/source lifetime before returning a decision.

This change is only the core prerequisite. It adds no listener, SubjectAccessReview parser, mapping store, API-server deployment, receipt, native Human session authentication or Workload coercion. The future SAR adapter must resolve mapping and grants within the same captured View, preserve source-owner fences, default deny unsupported requests, authenticate and bound ingress, and qualify API-server cache/failure/authorizer ordering separately. Kubernetes API access under this context does not claim end-client network enforcement or MFA.

Core tests cover cross-context isolation, ordinary network/guard behavior, invalid opt-in combinations, subject/scope isolation, permission/class/inherited-AAL/resource-AAL constraints, grant withdrawal on recompilation and exact default service serialization bytes. They do not qualify an inbound webhook or live cluster.
