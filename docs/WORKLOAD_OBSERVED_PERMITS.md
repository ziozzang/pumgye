# Native Workload observed projection permits

The optional `observed-authentication` feature adds `WorkloadObservedProjectionPermits.Issue/Observe`. This is a separate typed entrypoint: wire kind3, AAL0, a canonical signed Hopae `wobs1` epoch, and the native policy's `workload_users` grants are mandatory. Existing Service RPCs remain kind2 and use `users`. There is no fallback between the maps or between strict UTC and observed source time. Human authentication needs its own native session owner and is not supported by this entrypoint.

The fixed startup trust and endpoint resources create one persistent Workload SDK client. Incoming issuer, subject, epoch, revisions, timestamps, or numeric budgets cannot construct a checked capability. `CheckedObservedWorkload` has private fields and comes only from the actual authenticated Workload ObserveTime exchange, signature verification, exact request digest/scope binding and local suspend-inclusive admission checks. Source record misses, source expiry and native profile/application/key withdrawal refuse; signing an authentication proof does not grant resource access.

The permit owner captures the same exact compiled database/Kubernetes `View` as existing native decisions. It evaluates `evaluate_scoped_workload_resource` against `workload_users` and requires native network Allow, route ownership and projection plan observations. Service, resource, action, network, information class, role and assurance constraints remain conjunctive in the existing single compiler. Replacing that exact View, deleting the Workload grant or losing publication readiness prevents new issuance and observation of an old permit.

Before-callback receiver anchors and original route/plan/network expiries bound every grant. Authentication refresh intersects the previous local admission deadline; it cannot restart the original pre-TokenReview maximum one-second source budget. The signature remains private until post-sign route/plan RPCs, refreshed authentication, native owner seals and final source ticks succeed. No minimum of UTC and foreign process ticks is used.

The existing envelope fields and tags are reused. `PermitBinding.authority_epoch` and the report `clock_domain` match the issuing Pumgye process's `pobs1:<32-lowercase-hex-nonce>:<authority>` domain exactly. `owner_now_ms` is that process's suspend-inclusive elapsed tick. `proof_remaining_ms` describes the full signed permit lifetime for conservative replay retention only. `remaining_ms` is the shorter prerequisite-bound admission budget at the same sample; it never extends proof retention or renews a prerequisite. A downstream consumer must verify both authentication and permission independently and use the existing paired replay ledger. RPC or principal kind must not introduce another signer/key/purpose/nonce replay namespace.

## Activation

Build with `--features observed-authentication`. Supply `--workload-observed-permits --workload-authentication-live workload-live.json` plus `--authentication-trust`, `--permit-key`, `--network-live`, `--route-live`, `--projection-live`, and the existing mTLS gRPC options. The Workload live resource has the existing reference-only live JSON format: fixed issuer/HTTPS endpoint/server name, CA/client certificate/key paths, caller token environment-variable reference, and required `observed_clock_rates: {"source_ppm":500,"receiver_ppm":500}`. Values are explicit deployment assumptions, not a universal suggested rate. Missing or invalid bounds refuse activation. Tokens and key contents do not belong in status or logs.

`--projection-live` requires either the existing Service `--authentication-live` configuration or explicit Workload activation with its complete live configuration. Both activations require both configurations; one cannot fill in for the other. Existing Service startup/default behavior remains unchanged. Without the feature the new flags are absent; without activation the new handler has no owner and refuses. Observed operation requires a supported BOOTTIME backend; there is no legacy clock fallback.

## Verification scope

The repository tests exercise the actual Pumgye native compiler, private Workload SDK observation wrapper, typed sign/verify boundaries, exact owner replacement and generated RPC over mTLS with authenticated fixture peers. They cover same-subject class collision, Workload grant deletion, information class/AAL/network/resource refusal, nonrenewing refresh, malformed binding and scope floors, retirement during callbacks and post-sign work, and delayed final publication. Existing Service/default workspace suites remain regression gates.

Those peers are fixtures. These tests do not establish an actual Kubernetes TokenReview-to-Pumgye-to-consuming-Hopae-to-Hangang backend chain, live external Pod/ServiceAccount revocation timing, browser support, production deployment, or throughput. Typed consuming projection and dispatch require separate integration qualification. The existing legacy prerequisite-owner timing assumptions are unchanged; the new source clock is not a blanket clock guarantee for unrelated caches.
