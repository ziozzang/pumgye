# Pumgye 0.1.9 candidate — not adopted

This candidate adds explicit Kubernetes API authorization context, server-owned exact mapping compiled with existing grants, strict private v1 SubjectAccessReview decoding, and a default-off authenticated persistent HTTP/1 SAR listener. Source details and limits: [context](KUBERNETES_API_CONTEXT.md), [mapping](KUBERNETES_AUTHORIZATION_MAPPING.md), [wire](KUBERNETES_SAR_WIRE.md), [server](KUBERNETES_SAR_SERVER.md). Existing Service/Workload evaluators and network/guard defaults remain separate; no fake network/AAL evidence or Human/Workload authentication proof is made from SAR.

Actual local verified mTLS fixtures exercise the same connection through native Allow/Deny/Allow, strict caller isolation and pending TLS flush/current-View withdrawal/cancellation. Version0.1.9 metadata does not itself qualify a real Kubernetes API-server, production rollout or throughput. Signing, public release and adoption are held until parent-owned actual API-server gates and artifact verification. Existing published0.1.8 assets and operating configuration remain unchanged.

The0.1.9 production candidate is built with `--features pumgye-server/observed-authentication`, preserving the actual0.1.8 production RPC matrix. Build feature matrix must be recorded with each frozen raw: default features include SAR/strict native APIs, but exclude the `observed-authentication` feature's Service/Workload observed permit RPCs. Historical0.1.8 production raw included `pumgye-server/observed-authentication`. A default-only SAR qualification candidate must not silently replace that operating observed chain. An observed-feature raw, if separately prepared, needs its own exact hash/provenance and final gate. Neither compiled feature activates runtime owners by default.

Before adoption, require dedicated owned API-server qualification (v1, verified fixed caller, cacheAuthorizedRequests:false/cacheUnauthorizedRequests:false, failurePolicyDeny, correct authorizer order, no system:masters requester), source/grant withdrawal and outage/restart/rotation gates, and matching Root core/admin UI context compatibility. No existing main K3s authorizer changes are implied. SAR's raw send-boundary checks cannot recall kernel-accepted responses or previously admitted Kubernetes operations/streams. Persistent H1 is implemented; H2 per-stream ownership and extreme throughput remain pending. Native clock unsupported => opt-in SAR refuses without weakening legacy paths.
